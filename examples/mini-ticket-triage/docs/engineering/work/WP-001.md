# WP-001: Ticket Persistence and API

## Goal
Persist tickets as the authoritative state and expose create/read exactly as `contracts/openapi.yaml` defines. No AI call happens in this WP.

## Done Condition
The contract tests prove request/response shape; the integration tests prove a created ticket is readable after restart and that creation does not depend on any external provider. `schemas/001_create_ticket.sql` and the implemented migration must describe the same table.

## Invariants / Forbidden Changes
- Ticket creation never waits on, or rolls back because of, a model call (AC-01).
- `contracts/openapi.yaml` is frozen for this WP; any shape change stops the WP and opens a Change.
- Executed migrations are never edited; corrections are new migrations.

## Implementation Obligations
- Generate IDs server-side; reject client-supplied IDs.
- `state` starts at `NEW`; only WP-002 introduces triage transitions.
- Record `created_at`/`updated_at` in UTC.

## Review Lenses
R2: an independent reviewer checks migration reversibility, contract conformance and that no provider dependency leaked into the create path.

## Rollback / Recovery Notes
Greenfield: rollback is the down-migration plus reverting the PR. No data backfill exists yet.
